## A. Bugs — all fixed

Each was reproduced against a real project during review. A1 was fixed earlier;
A2–A6 are fixed together, and each entry keeps its original description with a
**Fixed** note saying what was done. Nothing in this section is left.

### A1. "Sometimes" and "only at setup" do nothing different

`src/layout/score.ts:101` is the only access rule:

```ts
if (!t.top && r?.access === "often") access++;
```

Only `often` scores. `sometimes` and `setup` are indistinguishable, so a
three-way control offers two behaviours. A user who changes `often` to
`sometimes` sees nothing happen and cannot tell whether the setting works.

**Fix:** make `setup` actively prefer sitting _under_ other trays — a
setup-only tray is the right thing to bury. Then the three values mean keep
clear / neutral / prefer underneath. Update the hint to describe all three and
to say it is a preference the optimizer weighs, not a rule.

### A2. A stale layout gives no hint that the plan needs re-running (fixed)

A layout stored under an older `geometryVersion` keeps its old geometry. The
only notice says the trays "won't mate with ones printed from it: reprint the
whole insert" — it never says _re-run the plan_, which is the actual fix. Two
separate investigations this session (a lip inset, then wall thickness) were
spent on layouts that were simply stale.

**Fix:** say the plan is out of date and offer to re-run it. The layout button
should also read "Update plan" rather than "Keep searching" in that state,
since re-fitting is what is needed.

**Fixed:** the notice now says the plan is out of date, names both geometry
versions and says "Update plan" rebuilds the trays with the current geometry. An
older geometry line counts as needing an update for the button label too.

### A3. The project menu will not close (fixed)

`src/ui/ProjectMenu.tsx` has no outside-click or on-select handler, so the menu
stays open until its own button is clicked again.

**Fix:** close on an outside click and on choosing a project.

**Fixed:** it also closes on Escape, with focus returning to its button.

### A4. The preview banner is unactionable and cannot be dismissed (fixed)

`src/app/App.tsx:318`: "Preview: saved projects and shared links may break
between versions." A user cannot act on it and cannot dismiss it.

**Fix:** remove it, or make it dismissible and say what the user should do
(keep a `.json` export). Leaning towards removing it.

**Fixed:** removed, with its style rule.

### A5. Warnings make the page scroll (fixed)

Several warnings at once push the layout out of view.

**Fix:** collapse or summarise them so the results stay visible.

**Fixed:** the layout messages show the first 3 (every error always, then the
most severe), and the rest fold behind a "Show all N messages" button.

### A6. "Doesn't fit" is reported as fact when it means "not found yet" (fixed)

Measured on a real project (Star Realms, 101 × 195 × 37 mm, stored layout at
geometry 0.4.0): warm-starting from the stored layout is feasible with 9 trays,
yet a cold run fails at 50 000 and at 300 000 iterations. The stored layout was
reached through 4 000 000 cumulative iterations. The box is extremely tight: two
stacks must each total exactly the 35 mm top plane, so only one partition of the
parts works. The old notice said the components "don't fit" and the box was "too
small by N mm", which a user would take as a proven fact and abandon a project
that does fit.

**Fixed:** the message now says no fit was found yet, names the iterations the
run made, says that is not proof, calls the figures the closest attempt so far and
says pressing "Update plan" again searches longer. The search itself is unchanged.
Because a failed run stores nothing, a plain repeat would redo the identical
search, so a user-pressed repeat for the same inputs now runs 3 times the previous
budget (no automatic retry). **Left open:** a box this tight may still not be found
cold within the time cap; finding it is a search problem, not a wording one.

## B. Design defects — specified in the companion document

Larger than bugs, smaller than features: each produces output a user reported as
wrong. All three are covered by `2026-10-13-minimal-trays-and-growth.md`.

- **B1. Stacked trays get stretched** (done, geometry 0.5.0), so identical
  components came out with different wall thicknesses, and a deck holder grew a
  pocket belonging to no component. Cause: a stack level held exactly one tray.
  Spec §3, §4. **Done:** a level is now a tray at the smallest size that holds
  its contents plus fillers for the rest of its room, and the minis tray from
  the real project comes out 110 × 28.4 with 1.2 mm walls on top of the Bits tray, as
  it does alone. **Also done** (geometry 0.5.1, schema 0.1.8, spec §4.2): the in-tray spare
  compartment is removed (a stretched deck's slack is a spacer, never a pocket), and
  `wallGrowth` is now `wallAbsorb`. The share links needed lossless compaction to stay under
  2 000 characters, and a stretched tray's spacer printed solid, heavier than the pocket
  (`small-tiles` about 100 g more). **Fixed in geometry 0.5.2** (spec §4.3): a spacer is an open
  box under the default `leftover` style, which took about 70 g back; the rest is the stretch
  itself, which the growth policy (C2) bounds.
- **B2. Fillers fragment.** A real layout produced four where two would do: two
  edge strips that are the same strip in different tree leaves, and an interior
  gap that should have been pushed to the edge. Spec §6.
- **B3. One component's trays scatter** (done), differently oriented and in different
  stacks. Same-orientation is a free tiebreak; same-stack is a score trade
  against `access`. Spec §6, §6.1. **Done:** two weak score terms; the three Starter-deck
  trays of the Star Realms project now share an orientation and, as the spec predicted,
  still stand in two stacks, because grouping them would bury two "often" trays.

- **B4. A latent CutFitError at a larger outer** (**done**, geometry 0.5.2, spec §4.3). Four causes
  fixed. The last, greedy channel placement stranding a pocket, is fixed by backing off in
  `placeCutouts`: while an owner has no cut, give up one cut of an owner that has another and place
  again. The property at 1 000 runs passes on all of seeds 1 to 12 (10 of 12 before); inputs are
  cases 4 and 5 of `cutfit.regression.test.ts`. A placement that already cut every owner is
  unchanged, so no version bump and no fixture changes. Not tried: ordering by constraint, which
  would change cuts of trays that work today.

## C. Features

### C1. Worth doing early — cheap, and they change whether output is trusted

- **Show the sizes derived from presets** (card format, count, sleeve) beside
  the editor, plus a correction multiplier, so a user can check the numbers
  without measuring every deck. The sizing layer already computes these.
- **Show the component name beside deck and item names** in the plan and 3D
  view, so several trays of one component read as a group.
- **Rename the box dimension labels** — "depth" reads as vertical; width /
  length / height is clearer. UI labels only, not schema fields.
- **Show which settings differ from their defaults**, with a restore button.
- **Make the play limit a setting.** 1.5 mm is a hard constant today and the
  warning cannot be dismissed.
- **Print-time estimate.** Much cheaper now the shell-and-core volume model
  exists.

### C2. Growth, fillers and dividers

All specified in `2026-10-13-minimal-trays-and-growth.md`:

- bounded auto-grow with per-axis user control, replacing `stretch`;
- filler merging (`mergeFillers`, `mergeRisers`), derived at print time;
- filler count as an explicit objective, and perimeter placement;
- the one-wall escape hatch for users who would rather not fit fillers;
- dividers, and how they are held.

### C3. Presentation and export

- An exploded 3D view in the assembly page and its print output.
- An optional XYZ axis indicator in the 3D viewer.
- Part numbers embossed on trays, matching the assembly instructions.
- Export as a modal, so leaving it does not switch a view mode back.
- A donation link on the export screen.
- Option descriptions as tooltips with screenshots.

### C4. Manual control

- Changing a tray's orientation by hand, in 90° steps. Needs `rotated` to
  become a turn count: schema bump, wide blast radius.
- Changing which layer a tray is on, including forcing an extra layer. Shares
  most of its machinery with B1, so build it after.

### C5. Larger, independent

Lids and cover sheet · flush stacking interlock (this is also the fix for the
"pyramid" stack when the lip is on, and the chamfered groove self-supports, so
no print supports are needed) · trays larger than the print bed, split and
joined · leftovers taller than the bed, split in Z · embossed labels · bundled
game presets library · calibration test print · inch input · cross-engine
determinism · frozen versioned builds.
